# Sprint 1.8a: Infrastructure as Code (IaC) - Supabase

## 1. The Constitution (Infrastructure Mandates)
1. **The IaC Mandate:** No database changes may be made manually via the Supabase Dashboard. Every table, column, RLS policy, and storage bucket MUST be defined in SQL within `supabase/migrations/`.
2. **Deterministic Environments:** The local agent and the E2E testing pipeline (Playwright) must operate against a local, Dockerized Supabase instance (`npx supabase start`).
3. **Seed State Integrity:** A `supabase/seed.sql` file must exist to inject a deterministic, baseline dataset (e.g., test users, a root Campaign wiki node, and nested child nodes) into the local database upon initialization.
4. **Environment Isolation:** The Nuxt `.env` file must be updated to route all database and storage requests to the local Supabase container (default: `http://127.0.0.1:54321`) during development and testing.

## 2. The Product Spec (Infrastructure Flows)
* **Flow 1: Local Orchestration:** A developer (or agent) clones the repository, ensures Docker is running, and executes `npx supabase start`. The local database provisions itself automatically.
* **Flow 2: Schema Catch-Up (Baseline):** The first migration creates the `wiki_nodes` table, enables the `ltree` extension, and sets up `tsvector` search, perfectly matching the state created in Sprints 1.1–1.7.
* **Flow 3: Sprint 1.8 Schema Evolution:** Subsequent migrations add the `entity_type` enum, the `cover_image_url` column, and provision the `wiki-assets` storage bucket with appropriate RLS policies.
* **Flow 4: Test Suite Hydration:** Before Playwright tests run, the database is hydrated with `seed.sql`, ensuring tests always interact with known `ltree` paths and node data.
